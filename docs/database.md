# Database operations

Everything about Postgres in this repo: how each environment differs, how to
dump and restore, how production's CNPG + S3 backup workflow actually works,
and the failure modes that have already bitten us.

---

## The two environments run different Postgres

This is deliberate, not drift. They need different things.

| | staging | production |
|---|---|---|
| What runs | plain `postgres:18-alpine` Deployment | CloudNativePG `Cluster` |
| Manifest | [`overlays/staging/postgres.yaml`](../overlays/staging/postgres.yaml) | [`overlays/production/database/postgres-cluster.yaml`](../overlays/production/database/postgres-cluster.yaml) |
| Namespace | `gami-staging` | `gami` |
| Instances | 1 | 1 (never HA — one node, nothing to replicate to) |
| Storage | 25Gi `local-path` | 20Gi `local-path` |
| Backup | **none, by design** | nightly base backup + continuous WAL → S3 |
| Superuser | `gami` | `postgres` (`gami` owns the database) |
| Credentials from | Ansible's `app_secrets` role | generated by CNPG |

Staging genuinely has **no backup at all**. Treat its data as reproducible.
If you need it to survive, dump it yourself (below).

Why the superuser differs: the official `postgres` image makes
`POSTGRES_USER` (`gami`) the bootstrap superuser, so there is no separate
`postgres` role there. CNPG keeps the conventional `postgres` superuser and
creates `gami` alongside it as the database owner. Every command below picks
the right one for you; it matters if you run `psql` by hand.

## Quick reference

```bash
set -a; source .env; set +a
cd ansible

# Dump (fetches the file back to ./dumps/)
ansible-playbook -i inventory/production.yml playbooks/db-dump.yml --limit gami-staging
ansible-playbook -i inventory/production.yml playbooks/db-dump.yml --limit gami-prod

# Restore — DESTRUCTIVE, see the warnings below
ansible-playbook -i inventory/production.yml playbooks/db-restore.yml \
  --limit gami-staging \
  -e database_restore_file=../dumps/gami-20260820T1200.dump \
  -e database_restore_confirm=true

# On-demand production backup to S3 (waits for completion)
ansible-playbook -i inventory/production.yml playbooks/db-backup.yml
```

`--limit` is required for dump and restore. `db-restore.yml` refuses to run
against more than one host — restoring one dump onto both environments is
never what you meant.

## Taking a dump

The playbook runs `pg_dump` inside the Postgres pod, writes to
`/var/backups/gami` on the node, verifies the file is non-empty, and fetches
it back to `./dumps/` on your machine (gitignored).

It always uses **`pg_dump`, never `pg_dumpall`**, with `--format=custom
--no-owner --no-privileges`. Each of those matters — see the next section.

To do it by hand instead:

```bash
# staging
sudo k3s kubectl -n gami-staging exec deploy/gami-postgres -- \
  pg_dump -U gami -d gami --format=custom --no-owner --no-privileges > gami.dump

# production (the primary pod name comes from the Cluster's own status)
POD=$(sudo k3s kubectl -n gami get cluster gami-postgres -o jsonpath='{.status.currentPrimary}')
sudo k3s kubectl -n gami exec "$POD" -c postgres -- \
  pg_dump -U postgres -d gami --format=custom --no-owner --no-privileges > gami.dump
```

## Why dumps break passwords

**Never use `pg_dumpall` here.** It dumps global objects, which includes:

```sql
ALTER ROLE gami WITH PASSWORD 'SCRAM-SHA-256$...';
```

— the *source* system's password hash. Restoring that silently overwrites
the target's password, and the app then fails with:

```
error: password authentication failed for user "gami"
```

This happened on staging on 2026-08-20. The app's credential lives in the
`gami-postgres-app` Secret, which the restore didn't touch, so the Secret and
the database disagreed.

`pg_dump` of a single database never touches roles or passwords, which is
why every command here uses it.

**If it already happened**, set the password back to what the Secret says,
rather than regenerating the Secret (which would leave the database on the
old password instead — the same problem mirrored):

```bash
PW=$(sudo k3s kubectl -n gami-staging get secret gami-postgres-app \
       -o jsonpath='{.data.POSTGRES_PASSWORD}' | base64 -d)

printf "ALTER USER gami WITH PASSWORD '%s';\n" "$PW" | \
  sudo k3s kubectl -n gami-staging exec -i deploy/gami-postgres -- psql -U gami -d gami
```

Piping it in keeps the password out of the node's process table. Then verify
over TCP the way the app connects — `-h 127.0.0.1` is essential, since a
plain socket connection is trusted and would prove nothing:

```bash
sudo k3s kubectl -n gami-staging exec deploy/gami-postgres -- \
  env PGPASSWORD="$PW" psql -h 127.0.0.1 -U gami -d gami -c 'select 1'
```

Related: `POSTGRES_PASSWORD` is only ever read by `initdb`, on the
database's **first** start against an empty volume. Recreating the Secret
later does not change the password inside an existing database — see
[`roles/app_secrets/tasks/main.yml`](../ansible/roles/app_secrets/tasks/main.yml)'s
header, which is why that role is generate-once.

## Restoring a dump

**Disable the target Application's auto-sync first.** This is the step
people skip, and it costs you the restore:

```bash
sudo k3s kubectl -n argocd patch app gami-staging --type=json \
  -p '[{"op":"remove","path":"/spec/syncPolicy/automated"}]'
```

Why: the migrate Job runs `npm run db:setup` → `drizzle-kit push`, which
reconciles the live schema to the app's `schema.ts` and **drops anything not
in it**. The Job carries `Replace=true,Force=true`
([`base/gami-migrate-job.yaml`](../base/gami-migrate-job.yaml)), so ArgoCD
deletes and recreates it on *every* sync — and with `selfHeal: true`, even a
`kubectl rollout restart` counts as drift and triggers one. Restore into an
auto-syncing Application and your data can be reshaped minutes later.

Then restore:

```bash
ansible-playbook -i inventory/production.yml playbooks/db-restore.yml \
  --limit gami-staging \
  -e database_restore_file=../dumps/gami-20260820T1200.dump \
  -e database_restore_confirm=true
```

The playbook takes its own **safety dump first**, into
`/var/backups/gami/gami-pre-restore-<timestamp>.dump` on the node. That
isn't ceremony: `pg_restore --clean` DROPs every object before recreating
it, so a restore that fails partway leaves the database emptier than it
started. If that happens, the safety dump is what you restore from.

Re-enable auto-sync afterwards:

```bash
sudo k3s kubectl -n argocd patch app gami-staging --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":{"prune":true,"selfHeal":true}}}}'
```

### Restarting the app afterwards

Use `delete pod`, **not** `rollout restart`:

```bash
sudo k3s kubectl -n gami-staging delete pod -l app=gami-webapp
```

`rollout restart` writes a `restartedAt` annotation into the pod template,
which ArgoCD sees as drift and corrects with a full sync — re-running the
migrate Job. Deleting a pod isn't drift; the ReplicaSet just recreates it.

### If the restore ran but the app can't connect

That's the password-drift case above, not a restore failure.

## How production's backups work

Production is the only environment that backs up. The moving parts:

```
CNPG Cluster (gami-postgres)
   │  spec.plugins → barman-cloud.cloudnative-pg.io  (isWALArchiver: true)
   ▼
Barman Cloud plugin  (cluster-operators/cnpg-barman-plugin/, cnpg-system)
   │  reads ObjectStore for destination + credentials
   ▼
ObjectStore (gami-postgres-backup-store)
   │  s3://gami-prod-backup/postgres-backups
   │  credentials ← Secret gami-postgres-backup-creds (created by hand)
   ▼
Hetzner Object Storage  (same bucket as Terraform state, different prefix)
```

Two independent mechanisms, and the distinction matters:

- **Continuous WAL archiving** — `postgresql.parameters.archive_timeout:
  "60s"` forces Postgres to close and ship a WAL segment every 60 seconds
  even if it hasn't filled to 16MB. This is what bounds data loss to about a
  minute and makes true point-in-time recovery possible.
- **Nightly `ScheduledBackup`** (`gami-postgres-nightly`, 02:00) — a base
  backup. This does *not* control how recent your recovery point is; it
  controls how much WAL has to be replayed to reach it, i.e. restore speed.

Retention is 30 days (`ObjectStore.spec.retentionPolicy`), pruned
automatically.

### One-time setup

The Barman Cloud plugin installs itself via ArgoCD
([`cluster-operators/apps-production/cnpg-barman-plugin.yaml`](../cluster-operators/apps-production/cnpg-barman-plugin.yaml)),
so the only manual piece is the credentials Secret:

```bash
sudo k3s kubectl create secret generic gami-postgres-backup-creds \
  --namespace gami \
  --from-literal=ACCESS_KEY_ID="<Hetzner Object Storage access key>" \
  --from-literal=ACCESS_SECRET_KEY="<Hetzner Object Storage secret key>"
```

Not committed to git, for the same reason as `ghcr-pull-secret` — a
long-lived storage credential with no rotation story of its own. The
placeholders are listed in [`.env.example`](../.env.example) so that file
stays the single answer to "what credentials does operating this repo need."

The bucket (`gami-prod-backup`) already exists — Terraform state uses it
under a different prefix. Only confirm the key pair can write to
`postgres-backups/`.

### Verifying it actually works

Don't trust a green `ScheduledBackup` object. Prove the path end to end:

```bash
ansible-playbook -i inventory/production.yml playbooks/db-backup.yml
```

That creates a `Backup`, waits for it, and fails loudly if it doesn't reach
`completed`. It exercises the operator, the plugin, the credentials and the
bucket in one go.

Check WAL is landing continuously, not just nightly:

```bash
POD=$(sudo k3s kubectl -n gami get cluster gami-postgres -o jsonpath='{.status.currentPrimary}')
sudo k3s kubectl -n gami logs "$POD" -c postgres | grep -i archive
sudo k3s kubectl -n gami get backup
```

### Changing backup parameters

All of it is in
[`overlays/production/database/postgres-cluster.yaml`](../overlays/production/database/postgres-cluster.yaml) —
edit, commit, push, let ArgoCD sync:

| Want to change | Field |
|---|---|
| Recovery granularity (data-loss window) | `spec.postgresql.parameters.archive_timeout` |
| Nightly backup time | `ScheduledBackup.spec.schedule` (6-field cron, seconds first) |
| How long backups are kept | `ObjectStore.spec.retentionPolicy` |
| Bucket / prefix / endpoint | `ObjectStore.spec.configuration.destinationPath` / `endpointURL` |
| WAL compression | `ObjectStore.spec.configuration.wal.compression` |

Bumping the plugin version is a one-line URL change in
[`cluster-operators/cnpg-barman-plugin/kustomization.yaml`](../cluster-operators/cnpg-barman-plugin/kustomization.yaml).

### Point-in-time recovery

Restoring to a moment in time is not the dump/restore path above — it's a
CNPG bootstrap. You create a **new** `Cluster` with
`spec.bootstrap.recovery` pointing at a completed backup plus a
`recoveryTarget.targetTime`, let it replay WAL to that instant, verify it,
then cut over.

Do a drill at least once, in a maintenance window, before you need it:

1. Insert a recognizable row; note the wall-clock time.
2. Bootstrap a throwaway `Cluster` with `recoveryTarget.targetTime` set to
   just after that.
3. Confirm the row is present — that proves WAL replayed, not just that the
   nightly base backup restored.
4. Delete the scratch cluster.

The exact `bootstrap.recovery` shape is version-specific to the CNPG release
and the plugin model; check
[CNPG's docs](https://cloudnative-pg.io/docs/) for the version pinned in
[`cluster-operators/cnpg/kustomization.yaml`](../cluster-operators/cnpg/kustomization.yaml).

## Migrations, and why they can eat your data

The app's `db:setup` is `drizzle-kit push && tsx scripts/seed.ts`.

`drizzle-kit push` is a **development-time schema sync tool**. It reconciles
the live database to `src/lib/db/schema.ts` and drops whatever isn't in
there. There are no versioned migration files in `gami-webapp` at all — no
`drizzle/` directory, and the Dockerfile doesn't copy one — so `push` is
currently the only mechanism.

Consequences worth knowing:

- Restoring a dump whose schema differs from the app's current `schema.ts`
  means the next sync will "fix" the difference by dropping things.
- The app's own `entrypoint.sh` also runs `drizzle-kit push` on container
  start, but Kubernetes never uses it: both
  [`base/gami-webapp/deployment.yaml`](../base/gami-webapp/deployment.yaml)
  and [`base/gami-migrate-job.yaml`](../base/gami-migrate-job.yaml) set
  `command:`, which replaces the image's `ENTRYPOINT`. Migrations happen in
  the Job only.
- `seed.ts` *is* idempotent — it checks for existing users and skips — so
  repeated runs don't duplicate data.

The durable fix is app-side: generate versioned migrations
(`drizzle-kit generate`), copy the `drizzle/` directory into the runtime
image, and switch `db:setup` to `drizzle-kit migrate`. Until then, treat
every sync as capable of running destructive DDL, and keep production's
backups healthy.
